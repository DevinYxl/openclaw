# 监控通知消息追加发送策略

## 背景

DBPool 等监控任务需要将多次执行结果追加到同一条消息卡片中，避免频繁刷屏。但当消息卡片丢失（如被删除）或整点切换时，需要智能判断是否追加还是新发。

## 最佳实践：三消息回溯判定法

### 核心逻辑

在每次发送前，**拉取群内最近 3 条消息**进行判断：

```python
def decide_send_strategy(target_card_id, recent_messages):
    """
    判定是追加(APPEND)还是新发(SEND_NEW)

    Args:
        target_card_id: 我们要追加的目标卡片消息ID
        recent_messages: 群内最近3条消息列表

    Returns:
        "APPEND" 或 "SEND_NEW"
    """
    # 场景1: 最近3条中包含目标卡片 → 正常追加
    if any(m.msg_id == target_card_id for m in recent_messages):
        return "APPEND"

    # 场景2: 最近3条都是短消息(非卡片) → 目标卡片已沉底/丢失，需新发
    if all(len(m.content) < 100 for m in recent_messages):  # 阈值可调整
        return "SEND_NEW"

    # 场景3: 其他情况(混合长短消息) → 保守策略：新发
    return "SEND_NEW"
```

### 判定规则详解

| 最近3条消息状态      | 判定结果 | 说明                                 |
| -------------------- | -------- | ------------------------------------ |
| 包含目标卡片ID       | **追加** | 目标卡片仍在视野内，继续追加         |
| 全是短消息(<100字符) | **新发** | 目标卡片已沉底或被删除，需开启新卡片 |
| 混合状态(有长有短)   | **新发** | 保守策略，避免追加到错误消息         |
| 消息数量不足3条      | **新发** | 群消息可能被清空，新开卡片           |

### 代码实现要点

1. **获取最近消息**

```python
recent_msgs = feishu_api.get_chat_history(chat_id, limit=3)
```

2. **消息长度判定**

- 短消息：纯文本、简短告警（通常 < 100字符）
- 长消息/卡片：监控报告、结构化数据（通常 > 100字符或包含卡片结构）

3. **消息ID缓存**

- 每次**新发**卡片后，立即将 `msg_id` 写入本地状态文件
- 每次执行时读取上次保存的 `target_card_id`
- 即使本地缓存丢失，也能通过"三消息回溯"找回或重建

### 异常处理

| 异常情况                 | 处理策略                                     |
| ------------------------ | -------------------------------------------- |
| API获取消息失败          | fallback到本地缓存，缓存有效则追加，否则新发 |
| 目标卡片不可编辑(被删除) | 捕获异常，自动转为新发策略                   |
| 消息长度判定模糊         | 保守策略：一律按短消息处理（即新发）         |

### 与整点逻辑的协同

原有的"整点(00分)强制新开卡片"逻辑保持不变：

- 整点时：强制 `SEND_NEW`
- 非整点时：执行上述"三消息回溯判定"

```python
if current_time.minute == 0:
    return "SEND_NEW"  # 整点强制新开

return decide_send_strategy(target_card_id, recent_messages)
```

## 收益

- ✅ 解决卡片丢失后追加失败的问题
- ✅ 避免整点无意义的新开卡片（如果旧卡片仍在）
- ✅ 自动适应群消息被清理的情况
- ✅ 防止追加到无关的短消息（如告警通知）
